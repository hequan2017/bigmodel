# Go 大模型应用开发平台：两天开发计划与模块设计

> 编制日期：2026-11-13  
> 文档版本：1.0  
> 交付定位：两天内完成可运行、可演示、可验证的 MVP。  
> 排期基线：3 名熟悉现有工程模板的开发者 × 2 天 × 8 小时，共 48 人时。  
> 本文性质：开发方案与验收计划，不代表已经完成代码、部署或测试。

## 1. 先确定两天能交付什么

原采购要求涵盖数据治理、知识检索、模型纳管、训练调优、智能体、技能生态、考试平台与终端等多个产品域。两天不能从零完成全部采购能力，也不能以占位页面、模拟进度或静态配置表宣称满足采购验收。

两天交付集中在两条真实业务链路：

1. **知识问答链路**：教师登录 → 创建知识库 → 上传资料 → 解析、切分和向量化 → 创建并发布教育问答助手 → 学生提问 → 显示回答与原文引用。
2. **考试链路**：教师维护客观题 → 固定组卷并发布 → 学生开始考试 → 自动保存 → 交卷 → 服务端判分 → 查看成绩。

所有展示为“可用”的功能必须实际调用后端并持久化数据。未接入的功能在本期菜单中不展示；如产品演示必须展示规划，则明确标识“规划中”，不能产生伪造的成功状态。

### 1.1 排期成立的前提

| 前提 | 具体要求 | 不成立时的处理 |
|---|---|---|
| 基础工程 | 有可复用的 Go API、登录认证、数据库迁移和后台页面模板 | 缩减范围，优先知识问答链路；不能仍承诺相同交付量 |
| 人员 | A：Go/模型接入；B：Go/考试与部署；C：前端/联调 | 单人方案见第 21 节 |
| 模型服务 | 已有可访问的 Chat 和 Embedding 服务，凭据、额度及模型名称可用 | 第一天上午先解决依赖；不可用时明确阻塞，不能用假回答替代 |
| 部署环境 | 有可以运行应用与 PostgreSQL 的机器，所需镜像或软件可取得 | 环境建设时间必须计入两天预算 |
| 数据 | 已准备允许使用的教学资料、标准问答和客观题 | 使用团队原创演示数据，不等待大规模数据采购 |
| 产品范围 | 单机构、单环境、少量演示用户、单台部署 | 多租户商业化、国产化全适配等单独估算 |
| 验收口径 | 验收 MVP 的真实链路与工程质量 | 不将本次结果直接等同于采购技术条款全部达标 |

### 1.2 本期范围与后续设计的标记

- **P0 / 两天交付**：进入本次排期，必须真实完成。
- **P1 / 后续增强**：有明确增量价值，但不占用本次承诺的工时。
- **完整平台设计**：为覆盖采购能力给出的目标方案；仅写入设计，不提前创建空服务、空表或未使用的抽象。

优先级下降时，先砍可选页面、图表、复杂交互与额外格式；不得砍服务端权限、考试计时、交卷幂等、密钥保护和真实数据持久化。

| 基础管控 | 预置账号、三种固定角色、资源归属校验、关键事件记录、基本健康检查 | SSO、组织结构、细粒度策略、完整运维面板、审计防篡改、干预机制 |
| 算子库 | 固定解析、切分、向量化、检索、Prompt 渲染、生成算子 | 可视化编排、条件/循环/并行、版本管理、扩展包和隔离执行 |
| AI 等级考试分布式系统 | 单实例在线考试业务闭环；等级标签；单选与判断题 | 多副本调度、高可用、容量验证、等级规则、证书与分布式运行证据 |
| AI 能力考试终端 | 浏览器考试页面、保存状态、倒计时、刷新恢复 | 原生/受管安全终端、设备绑定、防作弊、断网恢复、升级与设备运维 |
| AI 开发数据集 | 原创或授权的少量资料、问答及试题样例；来源清单 | 规模化清洗、标注、版本、质量评估、授权管理与训练数据导出 |

**边界说明：**

- RAG 问答不等于完成大模型训练。
- 一个应用内的 Prompt 配置不等于完成 Prompt 工程平台。
- 固定函数链不等于可自主规划的 Agentic 系统。
- 多个学生同时打开网页不等于分布式考试系统。
- 浏览器全屏或切屏提示不等于安全考试终端。
- 关键词匹配不等于已经完成中文全文检索；排名融合也不等于模型 Rerank。

## 3. 总体架构

### 3.1 两天采用模块化单体

Go 负责认证、业务规则、状态管理、任务编排、模型 API 调用、检索编排和考试事务。训练算法、模型推理、OCR 和音视频处理使用已有服务，后续通过适配器接入。

不在两天内拆微服务，不引入复杂服务治理，不自行实现训练框架，不为未来能力提前堆积中间件。

~~~text
浏览器管理端 / 教师端 / 学生端
                 |
          同源 HTTP API / SSE
                 |
              Go 应用
   +-------------+-------------+
   | 认证权限    | 知识库/RAG   |
   | 模型适配    | 应用/Prompt  |
   | 考试判分    | 日志/健康检查|
   +-------------+-------------+
          |          |          |
   PostgreSQL     本地持久卷    已有模型服务
   + pgvector     原始资料     Chat / Embedding
          |
   单进程后台循环
   文档处理 / 到期考试结算
~~~

### 3.2 技术选择

| 层次 | 本期选择 | 原因与限制 |
|---|---|---|
| HTTP 服务 | Go，沿用团队已有路由与中间件；无框架依赖时使用标准库 | 降低学习、迁移和调试成本 |
| 前端 | 复用现成后台模板与表单、表格、聊天组件 | 两天不重新设计组件库 |
| 数据库 | PostgreSQL | 统一保存业务状态、考试事务和审计记录 |
| 向量检索 | pgvector，演示规模先使用精确近邻查询 | 少一个独立向量数据库；先验证效果，再决定近似索引 |
| 原始文件 | 指定目录的持久化卷 | 不写入容器临时层；后续替换为对象存储 |
| 异步处理 | 单进程后台 worker + 数据库状态 | 只承诺单实例，不假装具备分布式任务队列 |
| 模型服务 | 服务端配置的现有 HTTP 接口 | 通过少量适配函数统一输入输出 |
| 对话输出 | SSE | 统一输出引用、文本增量、完成或错误事件 |
| 部署 | 一个应用服务 + 一个数据库服务；静态页面同源托管 | 控制部署和跨域复杂度 |

pgvector 默认支持精确近邻检索，小规模演示可不先配置 HNSW 或 IVFFlat。近邻检索的召回性质不能替代业务问答质量验证。技术依据见 [pgvector 官方说明](https://github.com/pgvector/pgvector#querying)。

### 3.3 模块职责

- Handler：参数解析、调用服务、转换响应；不直接承担评分和检索规则。
- Service：业务流程、权限判断、状态迁移、事务边界。
- Repository：明确的数据库读写；不过度封装通用 CRUD 框架。
- Provider：与外部 Chat、Embedding、后续训练及工具服务通信。
- Worker：领取待处理数据并调用 Service；不复制业务规则。

仅对真正可替换的外部依赖定义小接口，例如 ChatClient、EmbeddingClient。考试评分先用纯函数，不建立不必要的“评分插件框架”。

## 4. 基础管控模块

### 4.1 职责与本期页面

提供登录、当前用户、固定角色、资源权限、关键操作记录及健康检查。账号通过初始化脚本创建；本期不开发注册、找回密码、组织树或可配置权限编辑器。

### 4.2 固定角色

| 角色 | 可执行操作 |
|---|---|
| admin | 查看平台运行状态和模型配置；管理演示资源；排查失败任务 |
| teacher | 管理自己创建的知识库、应用、题库和考试；查看自己的考试成绩 |
| student | 使用已发布的演示应用；参加开放的演示考试；读取本人作答与成绩 |

本期采用单机构演示模式：已发布应用和考试对本机构预置学生开放。班级分配、个人授权与多机构隔离属于后续范围；若客户要求这些能力，则必须重新调整两天范围。

### 4.3 数据与权限规则

- users：用户 ID、登录名、密码哈希、角色、启用状态、创建时间。
- 资源表保存 owner_id；后端从认证上下文取得当前用户，不接受前端指定操作者。
- 学生不可读取草稿应用、未发布试卷、其他学生的作答或成绩。
- 教师只能管理本人资源；管理员访问也必须经过明确服务端规则。
- 检索引用和原文查看均复用同一权限检查，避免“问答接口受控、引用接口泄漏”。
- 对没有访问权的资源可统一返回 404，减少资源枚举；规则在全项目保持一致。

### 4.4 认证与日志

复用已有认证实现。若采用同源 Cookie 会话，应配置 HttpOnly，并对修改请求实施 CSRF 防护；正式环境使用 HTTPS。若已有安全的 Token 方案，继续沿用，不在两天内切换认证体系。

密钥由服务端部署配置注入，不进入前端、代码仓库、接口响应或普通日志。模型配置只暴露非敏感字段。

audit_events 至少记录：event_id、actor_id、action、resource_type、resource_id、result、request_id、created_at。登录失败可记录适度的来源信息，但不记录密码、完整 Token 或模型密钥。

关键发布与提交事件尽量与业务变更同事务落库。该实现提供基础留痕，不宣称防篡改审计已经完成。

### 4.5 完整平台扩展

后续增加统一身份认证、组织与项目空间、资源授权策略、密钥托管、操作审批、配额、审计留存与导出。租户隔离必须覆盖数据库、文件、向量、任务、日志和缓存，不能只增加 tenant_id 字段便宣布完成。

### 4.6 验收

- 三种账号菜单与 API 权限一致。
- 未登录访问业务接口被拒绝。
- 教师 A 无法修改教师 B 的知识库；学生 A 无法查看学生 B 的成绩。
- 密钥不出现在浏览器网络响应和应用日志中。

## 5. 模型接入与管理模块

### 5.1 本期实现

固定接入一个 Chat 服务和一个 Embedding 服务。页面展示模型名称、用途及连通性；模型端点和密钥由管理员部署配置决定，不开放任意 URL 输入。

“接入模型服务”仅说明能够调用已有服务，不意味着平台已经能一键部署开源模型。

### 5.2 数据与接口

model_profiles 保存：

| 字段 | 含义 |
|---|---|
| id / name | 平台内标识和展示名称 |
| kind | chat 或 embedding |
| provider_type | 当前实现的协议适配类型 |
| model_name | 提供商实际模型标识 |
| credential_ref | 服务端凭据引用，不是密钥正文 |
| embedding_dimension | Embedding 的输出维度；Chat 配置为空 |
| enabled | 是否允许调用 |
| config_version | 当前配置标识，便于定位历史运行 |

本期不提供复杂模型注册 CRUD；初始化配置后可通过列表与测试接口验证。

建议的 Go 接口：

~~~go
type ChatClient interface {
    Stream(ctx context.Context, req ChatRequest, emit func(ChatEvent) error) error
}

type EmbeddingClient interface {
    Embed(ctx context.Context, texts []string) ([][]float32, error)
}
~~~

平台内部 ChatRequest 使用明确的消息角色、消息内容、输出长度与采样参数；适配器负责转换为外部协议。HTTP 状态、超时和供应商错误统一转换为内部错误码。

### 5.3 调用策略

- 请求继承用户请求的 context；取消聊天后取消上游请求。
- 设置连接与响应超时，并限制全局并发，具体值在第一天连通性测试后固定。
- 外部服务限流和不可用应明确展示；不能自动生成“模拟成功”。
- Embedding 对明确可重试错误可做一次受限重试。
- Chat 在已经输出文本后不得自动重放整次请求，避免重复内容或额外计费。
- 不支持的参数不能静默丢弃，需在配置验证时提示。
- 调用记录保存模型标识、配置版本、耗时与结果；供应商未返回 Token 数时写 null，不伪造精确使用量。

### 5.4 完整平台扩展

增加厂商适配器、模型能力标签、版本管理、配额、成本、路由和熔断。模型部署模块单独管理镜像、权重、硬件需求、服务健康与发布回滚。

多模型互补需有可验证的路由规则，例如按任务类型选择模型，再用固定评测集对比。注册多个名称本身不等于完成多模型协同。

### 5.5 验收

Chat 能收到真实输出；Embedding 返回维度与知识库配置一致；错误密钥、上游超时、取消请求均能得到可辨识结果。

## 6. 数据管理与知识治理模块

### 6.1 本期输入和限制

- 支持 UTF-8 TXT 与 Markdown，不执行其中的脚本、链接或嵌入内容。
- 示例初始限制：单文件不超过 5 MiB，单文档最多 500 个片段。
- 文档数量和总字符数在演示环境设上限；超限明确拒绝，不静默截断。
- 上传文件名仅用于展示，存储路径由服务端生成。
- 内容类型、扩展名、编码和大小均进行校验。
- PDF/DOCX、扫描件、图片、音频、视频、网页与结构化连接器均不在 P0。

这些上限属于 MVP 产品限制，实际值在部署前按模型额度和机器资源固定。

### 6.2 核心数据

- knowledge_bases：名称、说明、owner_id、embedding_model_id、embedding_dimension、切分参数、状态。
- documents：知识库、原始文件路径、展示文件名、哈希、媒体类型、来源、使用范围、处理状态、失败原因、重试次数、时间戳。
- document_chunks：文档、顺序、文本、起止字符位置、标题路径、向量与向量模型标识。

本期不建设独立的通用资产中心。文档归属知识库，后续再提取 Asset/AssetVersion，以避免两天内同时维护资产、版本、解析块、索引任务四套抽象。

### 6.3 状态与处理流程

~~~text
queued → parsing → embedding → ready
             |          |
             +------→ failed → 手动重试 → queued

任何可访问状态 → disabled
~~~

1. 验证身份与知识库写权限。
2. 保存原始文件，计算内容哈希并写 documents。
3. 单进程 worker 读取 queued 文档。
4. 解析文本，保留标题和字符定位，生成规范化文本。
5. 按固定规则切片，调用 Embedding。
6. 确认向量数量、维度及数值有效后，在短事务中写入全部 chunks 并将文档改为 ready。
7. 查询只使用 ready 文档且再次检查知识库访问权。

外部模型调用不放在数据库事务内部。对于本期受限文件，可以先在内存中完成分块与向量计算，再一次提交；不能长期持有数据库锁等待网络服务。

### 6.4 切分规则

起始配置可采用每片约 600 个 Unicode 字符、重叠 100 个字符，优先在段落边界切分。这里是便于实现的初始值，不是效果最优保证。

每片保留 chunk_index、start_offset、end_offset 和标题上下文。引用中的偏移基于规范化后的文本，查看原文接口应返回同一文本版本，避免位置不一致。

需要验证中文、多字节字符、空文本、极短文本和超长段落；不能按字节截断 UTF-8。

### 6.5 重试、去重与停用

- 同一知识库相同内容哈希可返回已有文档，避免演示中重复计费。
- 重试必须替换失败尝试的临时结果，不能让一份文档生成重复片段。
- 本期单 worker 重启后，将上次中断的 processing 类状态标记为 failed，并允许人工重试；不宣称自动断点续传。
- 停用文档后立即从检索和引用读取中排除；物理清理进入后续维护，不在两天内实现复杂清理队列。
- 正在处理的文档被停用时，落库前重新检查状态，禁止任务将其重新置为 ready。

### 6.6 完整平台扩展

统一输出 ParsedBlock，包含 text、page、section、bbox、start_time、end_time、source_version 等定位字段，供不同解析器使用。

| 数据类型 | 后续处理方案 | 需要验证的重点 |
|---|---|---|
| PDF/DOCX | 文本、版面、表格解析；必要时 OCR | 页码、阅读顺序、表格结构、扫描件 |
| 图片 | OCR 与视觉描述分开保存 | 原图定位、描述可靠性、版权 |
| 音频 | 转写、分段、说话人信息 | 时间戳、长音频、识别误差 |
| 视频 | 音轨转写、关键帧、时间轴关联 | 音画对齐、重复内容、处理成本 |
| 网页 | 允许名单内抓取、正文提取、快照 | SSRF、认证、动态页面、更新失效 |
| 问答对 | 结构校验、问法规范化、标准答案版本 | 重复问题、冲突答案、来源 |
| 结构化数据库 | 只读连接器、元数据发现、受限查询 | 数据权限、查询超时、敏感列 |
| 半结构化数据 | CSV/JSON/表格映射为规范记录 | 字段映射、类型、坏行与批次追溯 |

完整治理增加资产版本、分类分级、保留期限、质量规则、血缘、归档与删除策略。新版本索引就绪后再切换，不让半成品影响正在使用的应用。

### 6.7 验收

合法文档可处理至 ready；失败可定位原因并重试；中文无乱码；引用能回到对应文本；停用后立即不可检索；未授权用户不能读取文件或片段。

## 7. 知识库与检索引擎模块

### 7.1 P0：先做好一种真实召回

本期只承诺向量语义检索。问答对样例可转换为“问题 + 标准答案”的文本资料，但这不等于已经建设独立问答对检索库。

检索流程：

~~~text
用户问题
  → 长度与权限校验
  → 使用知识库绑定的模型生成 Query Embedding
  → 在允许访问且 ready 的文档片段中查询 Top-K
  → 组装有限长度的证据
  → 将证据与用户问题交给模型
  → 返回回答和可核验引用
~~~

### 7.2 向量与数据库设计

- 一个知识库固定使用一个 Embedding 模型、版本与维度。
- 第一天先读取真实服务的输出维度 D，数据库迁移据此固定 vector(D)。
- 不能将不同维度的向量写入同一固定维度列。
- 即使维度相同，更换模型也应重建索引；不同模型的向量空间不可直接混用。
- 为 knowledge_base_id、document_id 和文档状态建立必要的普通索引。
- 演示规模使用精确查询，后续根据实际规模与延迟决定是否加近似索引。

示意查询，参数必须绑定：

~~~sql
SELECT c.id, c.document_id, c.content,
       c.embedding <=> $1 AS distance
FROM document_chunks c
JOIN documents d ON d.id = c.document_id
WHERE d.knowledge_base_id = $2
  AND d.status = 'ready'
ORDER BY c.embedding <=> $1
LIMIT $3;
~~~

上述 SQL 的前置条件是服务层已验证当前用户对该知识库的访问权。授权范围不能由客户端提交的 knowledge_base_id 单独决定。

### 7.3 统一候选结构

Candidate 至少包含：chunk_id、document_id、document_title、content、source_locator、retrieval_channel、rank、score、model_version。

初始 Top-K 可取 5，并受上下文预算限制。距离阈值必须根据本机构评测集校准，不直接承诺一个通用阈值。

模型输出采用片段标识引用。服务端只接受本次候选中的引用 ID；引用存在仅说明来源有效，不自动保证回答每个结论都被证据支持，仍需评测。

### 7.4 完整平台：四类知识库与多路召回

| 通道 | 存储与处理 | 返回证据 |
|---|---|---|
| 向量语义 | 向量字段/索引、查询向量化 | 文档片段与距离 |
| 全文检索 | 支持中文分词的全文索引，按词项相关性检索 | 命中正文、位置与排名 |
| 问答对匹配 | 标准问答、相似问法、匹配规则或向量 | 标准答案、来源、版本 |
| 数据库查询 | 参数化只读查询模板，后续再评估受限自然语言转查询 | 查询定义、数据时间与结果 |
| 图谱多跳 | 实体、关系、实体链接与受限图遍历 | 节点、边与完整推理路径 |
| 摘要检索 | 文档/章节摘要及对应源版本 | 摘要与可回溯原文 |

后续统一流水线：

1. 根据问题和应用配置选通道。
2. 各通道在权限范围内并行检索，设置独立超时。
3. 统一 Candidate，按文档版本与片段去重。
4. 使用基于排名的融合，例如 RRF；不直接相加量纲不同的原始分数。
5. 调用真实 Rerank 模型重新排序。
6. 复核权限、文档状态与版本，再组装上下文。
7. 在运行记录中保存每路耗时、候选数和降级原因。

关键词包含查询可以用于早期演示增强，但不得把它标为完整中文全文检索。RRF 是融合方法，Rerank 是单独的精排阶段。

### 7.5 验收与指标

准备 20 条人工确认答案和来源的教育问题，记录 Top-5 命中、引用正确性及无依据问题的响应。质量目标在第一天真实检索后设定，不能把未经测量的命中率写成既有能力。

本期硬性要求：引用 ID 有效、未授权资料不进入召回、模型失败不返回伪造答案。建议目标：至少 16/20 个有答案问题检索到预期证据，作为试运行目标而非通用性能保证。

## 8. Prompt 工程模块

### 8.1 本期设计

Prompt 保存在应用配置中，提供编辑、变量检查、调试与发布快照，不单独开发完整模板管理中心。

仅允许固定变量：

| 变量 | 来源 |
|---|---|
| question | 当前用户问题 |
| context | 本次授权检索得到的证据 |
| history | 当前用户会话中最近的成功问答 |

采用简单的白名单替换，不执行模板中的代码、表达式、文件访问或网络请求。对未知变量报错，对缺失变量给出明确提示。

### 8.2 消息组织

- 系统消息：应用角色、回答范围、引用要求和无依据时的策略。
- 历史消息：经过权限检查的最近对话。
- 证据区：带来源 ID 的外部资料，并明确其为数据。
- 用户消息：本次提问。

用户上传的文档与工具返回内容不能覆盖系统权限。Prompt 提示只能降低注入风险，真正权限必须由后端代码实施。

### 8.3 完整平台设计

- PromptTemplate / PromptVersion：模板正文、变量 Schema、适用模型、状态、作者、版本。
- BusinessRuleVersion：可执行的业务约束及说明，与应用版本绑定。
- TermEntry：术语、释义、别名、来源和所属领域。
- EvaluationSet / OptimizationRun：优化使用的数据、基线、候选版本和对比结果。
- 通过受控 API 渲染或调用指定版本模板；禁止客户端修改服务端必需规则。
- 在线优化先生成候选草稿，经评测后发布；批量优化不能无验证地覆盖当前版本。

“专家思维链管理”实现为专家编写的分析步骤、检查清单、规则与可解释结论模板，不依赖获取模型未公开的内部推理过程。

### 8.4 验收

模板缺少必需变量或包含未知变量时不能发布；调试使用草稿，学生使用发布快照；修改草稿不影响已发布版本。

## 9. 智能体与应用模块

### 9.1 本期应用类型

仅实现“教育知识问答助手”。用户选择知识库、填写名称与 Prompt、使用固定可用模型，调试后发布。

apps 字段：id、owner_id、name、status、draft_config、published_config、published_revision、published_at、created_at。

草稿与发布配置使用 JSONB 保存小型结构，包含 knowledge_base_id、chat_model_id、prompt、top_k、history_turns、generation_options。字段必须经后端 Schema 校验。

### 9.2 生命周期

~~~text
创建草稿 → 编辑 → 调试 → 发布
                        ↓
                   学生可以使用

继续修改草稿 → 再次发布 → 新请求使用新版本
~~~

每次运行开始时复制已发布配置快照，并记录版本，避免流式输出期间配置改变。停用应用后拒绝新运行；已有请求采用明确的继续完成或主动取消策略，本期建议继续完成并记录。

### 9.3 运行流程

1. 验证应用可用性和用户权限。
2. 创建 app_run，记录应用版本、用户和会话。
3. 加载该用户当前会话最近最多 3 轮成功记录，并限制总字符数。
4. 调用检索服务取得证据。
5. 渲染 Prompt，调用 ChatClient。
6. 通过 SSE 发送引用及文本增量。
7. 成功、失败或取消后记录最终状态和耗时。

会话历史是短期上下文，不等于长期记忆。不同用户、不同应用的会话不得交叉读取。

### 9.4 SSE 事件

| 事件 | 内容 |
|---|---|
| start | run_id、conversation_id、应用版本 |
| references | 本次可引用片段的 ID、标题和定位信息 |
| delta | 文本增量 |
| done | 最终状态、耗时、供应商提供的可选使用量 |
| error | 稳定错误码与用户可理解的说明 |

断开连接后终止上游请求并标记 canceled。已产生的部分输出可以留存，但必须显示“未完成”，不能作为成功问答写入后续历史。

### 9.5 完整平台：多种构建模式

| 模式 | 核心设计 | 额外验收 |
|---|---|---|
| 交互应用 | 表单输入、输出 Schema、界面渲染 | 输入校验、结果可解释、权限 |
| 工作流 | 有向图、节点版本、执行实例、分支与重试 | 重启恢复、失败节点重跑、幂等 |
| 多智能体 | 角色、共享上下文、消息路由、协作策略 | 循环终止、职责边界、成本预算 |
| Agentic | 意图判断、任务计划、工具选择、执行观察、结果检查 | 步数/时间/费用上限、授权、停止条件 |
| 长期记忆 | 显式可管理的记忆条目、来源、过期与用户授权 | 隔离、删除、错误记忆纠正 |

完整运行状态可扩展为 queued、running、waiting_approval、succeeded、failed、canceled，但本期没有外部写操作，不实现通用审批引擎。

自我反思采用结构化检查结果和有限次数修正，不记录或要求输出模型隐藏的内部推理。任何模型生成的计划都不能绕过工具权限。

### 9.6 六阶段管理的后续补齐

创建：配置与版本；调测：输入输出与步骤追踪；评测：固定数据集回归；发布：版本与灰度；运营：反馈、使用与成本；监控：延迟、失败率、异常调用和人工干预。

本期只覆盖创建、基础调试、发布与运行记录，不声称完整六阶段平台已经完成。

## 10. 算子库模块

### 10.1 本期采用固定算子

| 算子 | 输入 | 输出 | 失败处理 |
|---|---|---|---|
| extract_text | TXT/Markdown 原始内容 | 规范化文本及定位 | 编码或格式错误进入 failed |
| split_text | 文本、长度与重叠参数 | 带顺序与位置的片段 | 超限拒绝，不静默截断 |
| embed_text | 一批文本 | 对应向量 | 检查数量、维度、有效数值 |
| retrieve | 问题、授权知识库、Top-K | Candidate 列表 | 超时明确失败 |
| render_prompt | 已校验模板及变量 | 模型消息列表 | 变量错误阻止运行 |
| generate | 消息与模型配置 | 文本流及使用量 | 失败/取消明确结束 |

上述函数分别由导入流程与问答流程复用。采用统一的名称、版本、输入输出说明和错误语义，但不强制所有算子继承一个复杂父接口。

算子元数据可写在代码注册表中；本期不建立动态算子数据库、不支持上传任意脚本、不开发拖拽画布。

### 10.2 完整平台设计

OperatorDefinition 描述标识、版本、输入输出 Schema、配置 Schema、执行方式、资源要求与权限。WorkflowDefinition 绑定确定版本的节点与连线，WorkflowRun 保存配置快照，NodeRun 保存节点状态、产物引用和耗时。

先支持顺序和条件分支，再根据实际需求增加并行与循环。循环必须有次数上限；失败重试要区分纯计算、读操作和有外部副作用的写操作。

跨节点大对象通过对象存储引用传递，不把音视频或大矩阵塞进调度数据库。

### 10.3 验收

同一切分逻辑只有一份实现；导入和重试结果一致；运行失败可以定位到具体算子；算子日志不泄露密钥。

## 11. Skill 生态与 MCP 开放集成模块

### 11.1 本期边界

本期不实现动态技能安装、自然语言创建可执行工具、MCP 连接管理或任意代码执行。固定知识检索算子供问答流程调用，不将其宣传为已经完成技能生态。

若后续希望先增加一个可演示能力，应优先接入一个已存在的只读 MCP 服务，验证真实工具发现、参数校验、调用、超时和日志；该增量另排工时。

### 11.2 完整平台数据设计

| 实体 | 关键字段与作用 |
|---|---|
| SkillDefinition | 技能名称、业务说明、所有者、分类 |
| SkillVersion | 不可变版本、输入输出 Schema、步骤、权限与依赖 |
| SkillInstallation | 安装空间、固定版本、启用状态、授权范围 |
| ToolDefinition | 来源、参数 Schema、读写性质、超时、重试策略 |
| MCPConnection | 服务标识、允许的地址、传输配置、凭据引用、兼容版本、健康状态 |
| ToolInvocation | 用户、应用运行、工具版本、参数摘要、状态、耗时和结果引用 |

Skill 是业务能力的封装；MCP 是连接外部能力的一种协议。调用外部 MCP 服务时，平台承担 Host/Client 的职责；向外提供本平台能力时，需要另外实现 Server 适配层。概念依据见 [MCP 官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)。

实现时选择并固定一组经过验证的协议与 SDK 版本，按对端能力完成发现和调用，不把协议细节硬编码在业务 Service 中。

### 11.3 技能生命周期

~~~text
草稿 → Schema 校验 → 受控测试 → 发布版本 → 安装并授权 → 启用
                                                ↓
                                               停用
~~~

自然语言创建技能只生成描述、输入输出约束与步骤草稿，不能直接执行生成的任意代码。发布前检查依赖、权限、目标系统和测试结果。

调用流水线：检查用户与应用授权 → 校验参数 → 检查限流与预算 → 执行 → 校验结果 → 记录审计 → 返回结构化结果。

### 11.4 ERP、CRM、OA、SCM 集成

每类系统通过适配器处理 API 地址、认证、参数映射、分页、错误语义和数据权限。MCP 不会自动完成这些工作。

- 只读工具：可在限定条件下重试，并限制结果范围。
- 写入工具：必须定义幂等键、业务权限与失败补偿。
- 高影响操作：按机构策略要求人工确认，确认必须绑定具体参数与工具版本。
- 工作流：跨系统步骤记录外部业务 ID；不能依赖一次网络响应判断所有系统都已成功。
- 重试：没有证明幂等的写入操作不自动重放。

### 11.5 沙箱与隔离

HTTP 工具访问控制和代码执行沙箱是两件事。若允许用户上传代码，必须单独建设隔离执行环境，包括进程/容器边界、CPU/内存/时间配额、文件系统限制、网络策略、凭据隔离和产物出口。

外部工具返回的文字属于非可信数据，不得用于修改系统权限、自动扩大网络访问或泄露凭据。

### 11.6 后续接口与验收

建议接口：技能创建/版本发布、安装/停用、MCP 连接验证、工具发现、工具调用、调用记录查询。

验收应包含：真实工具发现与调用；未授权工具不可执行；超时可终止；写操作重试不重复落单；停用后新调用被拒绝；日志可关联用户、应用和外部业务 ID。

| 类型 | 平台配置重点 | 后端与验收重点 |
|---|---|---|
| 全量 SFT | 基础模型、训练/验证集、学习率、批次、长度、轮数 | 真实更新全量参数；保存权重与配置 |
| LoRA SFT | 目标模块、秩、缩放、dropout、基础模型版本 | 生成可加载适配器；证明与基础模型兼容 |
| 奖励模型训练 | 偏好样本、成对选择、奖励模型基线 | 真实训练并导出奖励模型，验证偏好评估 |
| 强化学习训练 | 策略模型、奖励模型、参考配置、采样与资源 | 后端真正执行对应强化学习过程 |
| 模型压缩 | 量化/压缩方法、校准集、目标运行环境 | 压缩前后质量、体积、延迟与兼容性 |

偏好优化方案可以作为单独能力评估，但不能将任何名为“偏好训练”的功能都等同于采购要求中的奖励模型训练与强化学习训练。

### 12.4 状态与后端适配契约

~~~text
draft → validating → queued → submitting → running → succeeded
            |            |          |         |
            +------------+----------+---------+→ failed
                                             ↓
                                      cancel_requested → canceled
~~~

建议接口边界：

~~~go
type TrainingBackend interface {
    Validate(ctx context.Context, spec TrainingSpec) error
    Submit(ctx context.Context, spec TrainingSpec, idempotencyKey string) (string, error)
    Status(ctx context.Context, externalID string) (TrainingStatus, error)
    Cancel(ctx context.Context, externalID string) error
    Artifacts(ctx context.Context, externalID string) ([]Artifact, error)
}
~~~

- 训练请求先持久化本地任务与幂等键，再提交后端。
- 网络结果不明确时先查询后端，不盲目重复提交。
- 回调携带后端身份验证与外部任务 ID；定时对账补偿回调丢失。
- 发出取消请求不等于资源已经释放，必须等待后端确认。
- 超参数使用白名单和类型约束，不透传任意命令、脚本或宿主路径。
- 进度来自后端事件或指标；未知进度显示未知，不按时间伪造百分比。

### 12.5 训练加速与模型部署

训练加速由后端能力提供，例如适配的精度模式、分布式训练、梯度累积与检查点策略。平台只展示后端实际支持的选项，并记录所用环境版本和硬件。

部署单独经历：产物校验 → 创建推理服务 → 加载模型 → 健康检查 → 预测测试 → 对外可用。训练成功不等于推理服务成功；LoRA 适配器必须同时记录所依赖的基础模型。

### 12.6 评估与质量门槛

评测数据与训练数据按版本隔离，检查重复和泄漏。基础模型与微调模型使用同一固定评测集对比，区分知识问答质量、格式遵从、任务指标、延迟与资源消耗。

任何质量提升都必须附评测版本、模型版本、样本规模与运行配置，不能仅凭一两个演示问答判断。

### 12.7 完整验收

至少验证真实成功任务、失败任务、取消、平台重启后的状态恢复、训练产物追溯、产物加载预测，以及各训练类型的专项证据。硬件预算和训练时长在模型规模、序列长度、数据量确定后单独测算。

## 13. AI 开发数据集模块

### 13.1 两天演示包

建议准备三类小数据，不依赖大规模采集：

| 数据 | 建议数量 | 用途 |
|---|---|---|
| 教学资料 | 3～5 份原创或授权 Markdown/TXT | 验证上传、切分、检索与引用 |
| 标准问答 | 20 条有依据问题 + 5 条无依据问题 | 验证召回、引用和无依据响应 |
| 客观试题 | 20 道单选/判断题 | 演示题库、组卷、保存与判分 |

这些是测试样例，不等同于采购级 AI 开发数据集。数量是计划建议，本文没有实际生成该数据包。

### 13.2 数据格式

资料清单包含：sample_id、title、relative_path、source、license_or_permission、allowed_usage、language、checksum、created_at。

问答记录包含：question_id、question、expected_answer、expected_document、expected_evidence、answerability、tags。

试题记录包含：question_id、type、stem、options、correct_answer、score、level_code、knowledge_tags、source。

标准答案只保存在教师/评测侧，不能作为学生试卷接口的附加字段返回。

### 13.3 MVP 实现方式

资料走现有上传链路，问答评测文件由开发人员使用，试题通过初始化脚本或普通题目表单导入。两天内不额外建设数据标注中心。

### 13.4 完整平台设计

建立 Dataset → DatasetVersion → DatasetSplit → Sample 的版本结构；样本保存来源、授权、标签、审核与去重信息。训练任务引用固定版本，不能读取随时变化的“当前目录”。

支持格式校验、重复样本检测、敏感信息识别、标注任务、双人复核、质量报告、数据集导出和版本差异。训练/验证/测试划分应按数据来源或实体合理隔离，避免近重复样本泄漏。

## 14. AI 等级考试后台模块

### 14.1 P0 产品边界

- 题型：单选题、判断题。
- 组卷：教师勾选题目，设置分值，形成固定试卷。
- 考试：设置等级标签、开放/截止时间、作答时长。
- 考生：使用预置学生账号；每人每场一次作答。
- 判分：服务端确定性判分，不调用大模型。
- 成绩：教师查询本人考试成绩，学生只看本人总分与提交状态。

不实现主观题、编程题、代码执行、AI 自动评分、随机组卷、证书、补考或监考。等级字段是业务分类标签，不代表已建立权威等级认证体系。

### 14.2 核心表

| 表 | 关键字段 | 约束 |
|---|---|---|
| exam_questions | id、owner_id、type、stem、options、correct_answer、default_score、level_code、tags、status | 题型与答案合法；分数为非负整数 |
| exams | id、owner_id、title、level_code、status、open_at、close_at、duration_seconds、published_at | close_at 大于 open_at；时长为正 |
| exam_items | id、exam_id、source_question_id、order_no、题面/选项/答案快照、score | exam_id + order_no 唯一 |
| exam_attempts | id、exam_id、user_id、status、started_at、deadline_at、answer_revision、submitted_at、submit_reason、total_score | exam_id + user_id 唯一 |
| exam_answers | attempt_id、exam_item_id、answer、awarded_score、saved_at | attempt_id + exam_item_id 唯一 |

题库与试卷分开。考试发布后使用 exam_items 快照，不能在判分时重新读取随时可编辑的题库原题。

### 14.3 草稿组卷与发布

1. 教师仅选择自己有权限的题目。
2. 草稿阶段保存或更新 exam_items，允许调整顺序与分值。
3. 发布事务锁定 exams，验证题目、选项、答案、总分和时间窗口。
4. 将当前草稿内容冻结并把考试设为 published。
5. 发布后不允许修改题面、正确答案与分值；若必须修改，创建另一场考试。
6. 草稿编辑与发布都锁定同一考试记录，避免并发编辑绕过冻结检查。

学生响应必须使用专用 DTO，只包含题目 ID、题干、选项、题型、顺序与分值。禁止直接序列化包含 correct_answer 的数据库实体。

### 14.4 开始考试与计时

开始接口校验：学生身份、考试已发布、当前时间在开放窗口内。

~~~text
deadline_at = min(started_at + duration_seconds, exam.close_at)
~~~

使用数据库时间作为判定基准。重复开始通过 exam_id + user_id 唯一约束返回原有作答，不创建第二份记录，也不重置计时。

前端倒计时仅是展示。保存、交卷与恢复请求均由服务端检查 deadline_at。

获取数据库行锁之后再读取当前数据库时刻进行截止检查；不要把等待锁之前的时间当作最终判定时间。避免长事务中的固定起始时间让晚到请求继续写入。

### 14.5 自动保存与并发版本

MVP 每卷最多 50 道客观题，采用完整答案快照，减少增量合并复杂度。

保存请求包含 expected_revision 与 answers：

~~~json
{
  "expected_revision": 3,
  "answers": [
    {"item_id": "item-1", "answer": "B"},
    {"item_id": "item-2", "answer": "true"}
  ]
}
~~~

服务端处理：

1. 开启事务，对当前 attempt 加行锁。
2. 校验用户归属、in_progress 状态、截止时间和版本。
3. 验证每个 item_id 属于当前试卷，且答案符合题型；重复 item_id 直接拒绝。
4. 版本不一致返回 409，不覆盖新答案。
5. 用本次快照替换已保存答案；快照未包含的题目表示当前未作答。
6. answer_revision 加一，返回最新 revision 和 saved_at。

同一浏览器的保存请求串行发送，不能并行提交多个版本。出现 409 时保留当前页面答案，读取最新服务端状态并提示用户处理冲突，不静默覆盖。

数据库行锁的行为依据见 [PostgreSQL 行级锁说明](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)。

### 14.6 交卷与判分

统一实现 FinalizeAttempt，由主动交卷、超时扫描和状态恢复调用。

~~~text
不存在作答 → in_progress → submitted
                            |
                  submit_reason = manual / timeout
~~~

主动交卷流程：

1. 前端等待最后一轮保存成功，并携带已确认的 answer_revision。
2. 服务端开启事务，锁定 attempt，校验用户。
3. 若已提交，直接返回原有结果，保证重复交卷幂等。
4. 若当前时间已到期，忽略新答案和版本差异，以已保存答案做 timeout 结算。
5. 若仍在有效期内但版本不一致，返回 409，要求同步后重试。
6. 用 exam_items 的冻结答案评分。
7. 同一事务写入逐题得分、总分、submitted_at、submit_reason 与 submitted 状态。
8. 提交事务后返回结果。

判分不访问外部服务，保证持锁时间短。单选和判断采用规范化后的精确比较，未作答得 0 分；本期不设置部分得分规则。

### 14.7 到期自动结算

单进程每隔固定时间扫描已到期且未提交的作答，例如每 30 秒一次。扫描只负责找到记录，最终仍调用 FinalizeAttempt。

查询作答和主动交卷也触发到期检查。定时扫描与用户交卷并发时，依靠同一行锁和终态检查只结算一次。

重启后继续扫描数据库中的到期记录，不依赖进程内计时器记忆每个学生的截止时间。

### 14.8 权限与结果展示

- 教师仅查看本人考试成绩。
- 学生仅查看本人的作答与总分。
- 正确答案与解析本期默认不向学生开放。
- 未发布试卷无法通过猜测 ID 读取。
- 普通访问日志不记录完整试卷答案或学生个人敏感信息。
- 发布、开始、交卷和重要异常记录 request_id，方便关联故障。

## 15. AI 能力考试浏览器端与安全终端设计

### 15.1 两天浏览器端页面

| 页面 | 内容与行为 |
|---|---|
| 可参加考试列表 | 名称、等级、开放时间、截止时间、状态 |
| 开始确认 | 显示考试时长与服务端规则；点击后取得固定截止时间 |
| 作答页 | 单页题目列表、题号导航、选择答案、倒计时、保存状态 |
| 提交确认 | 显示未答数量，先保存后交卷；保存失败时明确提示 |
| 结果页 | 本人总分、提交时间、手动/超时状态 |

页面不追求拖拽、复杂图表或多种布局，优先保证保存和状态恢复可解释。

### 15.2 保存交互

- 答案变更后防抖保存，例如 800 毫秒。
- 存在未保存变更时每 10 秒补充尝试。
- 页面显示“保存中 / 已保存 / 保存失败 / 版本冲突”。
- 刷新后从服务端恢复已保存答案和原始截止时间。
- 断网时保留当前页内存中的答案并提示，恢复后仅在截止前重试。
- 两天版本不承诺离线答题可靠性；关闭页面前未保存的数据可能丢失。
- 修改本机时钟、重复点击开始、刷新页面都不能延长考试。

SSE 用于问答输出，考试保存使用普通 HTTP 接口，不为本期考试引入 WebSocket。

### 15.3 真正安全考试终端的后续设计

安全终端应作为独立产品能力，明确支持的操作系统与受管设备条件，再设计：

- 设备身份、注册与绑定。
- 应用和外设限制策略。
- 考试资源的安全分发、密钥与本地缓存保护。
- 断网保存、恢复、冲突与服务端确认协议。
- 客户端版本签名、升级、健康检查和远程运维。
- 监考事件采集、误报处理、申诉与机构授权。

浏览器全屏、焦点变化和切屏次数只能作为辅助信息，不能代替系统级限制，也不能据此承诺防作弊。

## 16. 分布式运行、运维与可观测性模块

### 16.1 P0 运行方式

本期只有一个 Go 应用实例和一个数据库实例。文档 worker 与到期结算循环运行在同一个应用中。

提供：

- liveness：进程能正常处理请求。
- readiness：数据库及必要本地目录可用。
- 模型连通性检查：单独展示，不因 Chat 上游故障让考试服务一起变为不可用。
- 结构化日志：request_id、user_id、模块、操作、耗时、错误码。
- 运行记录：文档失败原因、问答运行状态、考试提交结果。
- 必要并发上限：限制文档向量化和 Chat 请求，避免拖垮考试接口。

P0 不开发通用数据看板。必要的统计可在现有列表显示数量，不新增独立 BI 或监控平台。

### 16.2 后续多副本设计

1. API 服务无状态化，统一会话策略，所有实例使用共享存储与一致时间基准。
2. 文档处理任务增加持久化任务表、领取租约、心跳与过期恢复。
3. 多 worker 使用数据库锁或队列分配任务，重试仍依赖业务幂等。
4. 队列按照“至少一次投递”设计，不能假设天然只执行一次。
5. 考试评分继续通过数据库事务约束状态，避免使用 Redis 锁替代最终一致性约束。
6. 引入数据库高可用、备份恢复、容量测试、负载均衡和必要限流。
7. 训练与推理计算资源单独调度，避免与考试 API 抢占资源。

### 16.3 考试容量验证

容量基于实际考生数、答题保存频率、开考突发、交卷突发和成绩查询计算。不能把接口 QPS 直接换算为“支持多少人考试”。

至少分别测试：集中开始、稳定保存、同时交卷、数据库恢复、API 实例重启。故障期间计时、补时和补考策略需要业务规则，而不是仅靠技术重试决定。

### 16.4 运维与干预

完整平台增加任务暂停/取消、应用停用、工具禁用、资源配额、告警、数据备份、恢复演练、日志留存与可审计的人工干预。

备份必须同时考虑数据库、原始资料、模型产物和配置，定义可接受的数据丢失窗口与恢复时间，并以恢复演练验证。
